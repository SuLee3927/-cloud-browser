# 安卓视觉操作与微信真机实战

这份记录关注“隧道已通以后，AI 如何稳定操作界面”。内容来自模拟器与 USB 真机的实际部署经验，
但示例均已脱敏，不包含设备序列号、账号、服务器地址或聊天内容。

## 1. 坐标不是浏览器坐标

Android 的 `screencap` 截图通常就是设备真实像素；`input tap x y` 也使用同一套像素坐标：

```bash
adb -s "$ANDROID_SERIAL" shell wm size
adb -s "$ANDROID_SERIAL" shell screencap -p /data/local/tmp/screen.png
adb -s "$ANDROID_SERIAL" pull /data/local/tmp/screen.png ./screen.png
adb -s "$ANDROID_SERIAL" shell input tap 800 1200
```

如果截图原图为 `1600×2560`，直接从原图量到的 `(800,1200)` 可以原样点击，**不要套用浏览器截图的
缩放倍数**。若查看器把图片缩成 `800×1280` 后再量坐标，则需换算：

```text
设备 x = 查看器 x × 1600 / 800
设备 y = 查看器 y × 2560 / 1280
```

生产工具最好在每张截图旁返回：

- 原始图片宽高；
- 坐标是否 1:1；
- 当前设备标识（用别名，不暴露真实序列号）；
- 当前前台包名。

## 2. 每一步都按“截图—动作—复核”执行

可靠流程不是连续猜坐标，而是：

```text
截图 → 判断当前页面 → 点击／滑动／输入 → 等待界面稳定 → 再截图确认
```

建议：

- 普通点击后等待约 300–700ms；页面跳转或相册加载可更久。
- 键盘弹出、横竖屏变化、弹窗出现后，旧坐标立即作废。
- 不要因为 ADB 命令退出码为 0 就宣称操作成功；必须看下一张截图。
- 发送、发布、删除等外部写操作，在执行前确认目标和内容，执行后确认页面变化。
- 多设备环境每条命令显式传 `-s "$ANDROID_SERIAL"`，禁止依赖“当前默认设备”。

## 3. 有元素树时优先元素树

先尝试：

```bash
adb -s "$ANDROID_SERIAL" shell uiautomator dump /data/local/tmp/window.xml
adb -s "$ANDROID_SERIAL" pull /data/local/tmp/window.xml ./window.xml
```

XML 中常见节点：

```xml
<node text="发送" clickable="true" bounds="[1320,2210][1570,2330]" />
```

可点击中心点：

```text
x = (1320 + 1570) / 2
y = (2210 + 2330) / 2
```

匹配同名文字时，优先面积更小、更具体且 `clickable=true` 的节点；多个匹配必须要求索引或结合父级区域，
不要永远点第一个“确定”。

## 4. 元素树为空，不等于 ADB 坏了

真机上可能出现：

```xml
<hierarchy>
  <node package="目标应用" bounds="[0,0][0,0]" />
</hierarchy>
```

判断顺序：

1. 回到系统桌面再 dump。
2. 桌面能得到大量节点、目标 App 只有 `0×0` 空根：目标 App 主动隐藏或未暴露元素树。
3. 桌面也为空：再查 USB 调试、授权、锁屏、`uiautomator` 进程和系统限制。

目标 App 单独隐藏时，正确降级是截图＋坐标；不是反复重装 ADB，也不是把空 XML 当成旧页面继续点击。
OCR 可以补文字定位，但会增加体积和误识别，截图已经足够时不必默认安装。

## 5. 模拟器与真机的主要差异

| 项目 | 模拟器 | USB 真机 |
|---|---|---|
| ADB 发现 | 常需 `adb connect 127.0.0.1:端口` | 接线并接受 RSA 授权 |
| 重启恢复 | 模拟器端口可能变化／需重连 | USB 重插后通常自动恢复 |
| 元素树 | 通常较完整 | 部分 App 会隐藏 |
| 网络身份 | 模拟器环境明显 | 真实设备、真实系统网络 |
| 文件速度 | 通常较快 | 经过 SSH＋Windows ADB＋USB，可能更慢 |
| App 风控 | 可能识别模拟器 | 风险较低，但 ADB 高频自动化仍可能异常 |

不要把模拟器适配里的默认分辨率、输入法包名、ADB 端口直接写死到真机配置。

## 6. 中文输入：临时切换，立刻归还

`adb shell input text` 对中文／Emoji 支持不可靠。可安装开源 ADB 输入法并采用 base64 广播：

```bash
adb -s "$ANDROID_SERIAL" shell ime enable com.android.adbkeyboard/.AdbIME
adb -s "$ANDROID_SERIAL" shell ime set com.android.adbkeyboard/.AdbIME
adb -s "$ANDROID_SERIAL" shell am broadcast \
  -a ADB_INPUT_B64 --es msg 'UTF-8文本的base64'
adb -s "$ANDROID_SERIAL" shell ime set '用户原输入法组件名'
```

必须用 `try/finally` 确保异常时也切回原输入法。安装前记录：

```bash
adb -s "$ANDROID_SERIAL" shell settings get secure default_input_method
adb -s "$ANDROID_SERIAL" shell ime list -s
```

输入只负责填入当前焦点，不应把“填字”和“点击发送”合成一个不可检查的黑盒动作。

## 7. 服务器图片为什么不会自动出现在真机相册

AI 工作区截图默认存在服务器任务档案中，真机微信无法直接看到。稳妥流程：

1. 用户或任务明确指定一枚 `artifact id`。
2. 服务端只读取这一枚档案。
3. 经 ADB 推入 `/sdcard/Pictures/AiWorkspace/`。
4. 发送媒体扫描广播。
5. 微信相册选择该专属相册中的图片。

不要实现“同步整个服务器目录”或“列出真机全部相册”。普通文件放入
`/sdcard/Download/AiWorkspace/`，由目标 App 主动拉起系统文件选择器。

## 8. 文件推送为什么需要更长超时

文件实际链路是：

```text
服务器档案 → SSH 反向隧道 → Windows ADB server → USB → 真机存储 → 媒体扫描
```

单图可能很快，多图或较大文件可能超过统一 60 秒。建议：

- 只给“任务档案推送真机”配置 120–180 秒；
- ADB `push` 自身也设置合理上限；
- 普通截图／点击仍保持 30–60 秒快速失败；
- MCP 超时不代表文件一定没落盘，重试前先检查专属目录，避免重复文件。

## 9. 微信真机案例中的典型现象

### 微信能截图、能点，但 `read` 为空

先用桌面做对照。若桌面 XML 正常、微信只有空根节点，按第4节降级，不要误报“真机通道断了”。

### 图片已经推入相册，但点选动作偶发被官端拦截

先看服务器 MCP 调用日志：

- 推送、打开相册都到达服务器；下一次点击完全没有请求：拦截发生在模型／连接器平台侧。
- 请求到达服务器并返回 403／超时：再查自己的 allowlist、前台包与隧道。

平台侧拦截可能是对“通用坐标点击＋私人相册”的误判。不要通过隐藏工具语义绕过；可隔一段时间、在用户明确指定
图片与接收人后重试。长期方案是提供语义明确的“发送指定任务档案”工具，入参包含任务、档案、接收人和用户授权，
并在服务端限制只能访问任务档案。

### App 将模拟器判为异常环境

改用真实 USB 设备能消除“模拟器”这一明显信号，但不代表可以高频自动化。保持：

- 用户发起任务；
- 无自动轮询、无人值守群发；
- 操作频率接近正常人工；
- 登录、设备验证由账号所有者完成；
- 支付与账号安全页不自动操作。

## 10. 微信专用真机的最小权限模型

推荐把真机控制限制为：

```text
允许：目标微信包、由微信拉起的系统文件选择器
允许：截图、点击、滑动、临时输入、任务档案推送
拒绝：启动其它 App、遍历原相册、访问支付／账号安全、后台轮询、自动群发
```

如果用户按 Home 或自行切到别的 App，后续 AI 动作应返回“当前前台不在 allowlist”，而不是继续盲点。

## 11. 日志要能回答三个问题

排障日志至少记录：

1. 官端是否真的发出了工具调用？
2. MCP 是否把调用转给后端？
3. ADB 是否把动作交给了目标设备？

不要记录聊天正文、输入内容、相册文件名或访问令牌。推荐只记：时间、任务ID、动作类型、设备别名、耗时、结果码。
